## 1. 从一个简单问题开始

CAN 经典帧的数据区**最多 8 字节**。这是硬件限制，没法改。

那如果我想发 20 字节的数据——比如一条诊断命令 `"HELLO AUTOSAR CAN TP!"`——怎么办？

**直觉反应**："分开发不就行了？第 1 帧发 8 字节，第 2 帧发 8 字节，第 3 帧发 4 字节。"

方向对了。但紧跟着三个问题：

1. **接收方怎么知道"这三帧是一起的"？**——万一总线上同时有别的设备也在发数据，怎么区分？
2. **接收方怎么知道"总共要收多少帧"？**——第 1 帧就被告知总长度，还是收到最后一帧才知道？
3. **接收方处理不过来怎么办？**——比如缓冲区快满了，能不能让发送方"慢点发"？

ISO 15765-2 这个国际标准就是用来回答这三个问题的。**CanTp 是这个标准在 AUTOSAR 中的实现。**

## 2. 回顾 + 一个新类比

还记得第 4 篇的快递包裹比喻吗？

> 同一个包裹，寄件人叫它"包裹"、快递员叫它"件"、收件人叫它"快递"——东西没变，只是不同角色眼中的称呼不同。AUTOSAR 也一样：同一个 `PduInfoType`，在 Com 层叫 **I-PDU**，在 CanTp↔CanIf 之间叫 **N-PDU**。

这个比喻解释了"名字"的问题。但还有一个"尺寸"的问题没解决——**CAN 帧最多装 8 字节，大于 8 字节的 I-PDU 怎么办？**

这里引入第二个比喻：搬家公司拆装沙发。

```
你要运一张 3 米长的沙发（20 字节数据），但货车车厢只有 2 米宽（CAN 帧 8 字节）。

搬家公司（CanTp）的做法:

  ① 先把沙发拆成 3 段：座垫、靠背、扶手（分段）
  ② 给每段贴一个标签：写着"第 1/3 段"、"第 2/3 段"、"第 3/3 段"（PCI 字节）
  ③ 第一段还额外写着"总共 3 段"（首帧 FF 携带总长度）
  ④ 送到你家后，按标签顺序拼回完整的沙发（重组）

  如果在拆的过程中发现你家门口太小：
  ⑤ 搬家公司说"每次只送 2 段，间隔 1 分钟"（FC 流控）
```

**CanTp 就是那个搬家公司的拆装工人。** 大数据包（I-PDU）进 → 切成小块（N-PDU），每块刚好塞进一个 CAN 帧 → 发给 CanIf → 硬件发出。对端收到后，按标签拼回原样。

## 3. 从"N-PDU 的格式"到"N-PDU 的交互"

你在第 4 篇已经学过四种帧的 PCI 编码：

| 帧类型 | PCI | 用途 |
|--------|-----|------|
| **SF** | `0x0N` | 单帧，≤7 字节，一帧搞定 |
| **FF** | `0x1N NH` | 首帧，携带 12-bit 总长度 |
| **CF** | `0x2N` | 连续帧，N=序号 (0-15 回绕) |
| **FC** | `0x30 BS STmin` | 流控帧，接收方控制发送节奏 |

第 4 篇的重点是"**每个帧标签长什么样**"——这是 N-PDU 的 *静态格式*。

本篇的重点是"**这些帧之间怎么交互**"——这是 CanTp 的 *动态协议*。回到搬家公司的比喻：

> 搬家公司（CanTp）不只是给每段沙发腿贴个标签（第 4 篇的内容），更重要的是**按什么顺序发、发多快、对方说停怎么办**（本篇的内容）。

下面从"帧的交互"视角重新审视这四种帧：

### 3.1 SF — 最简单的交互：一帧结束

SF 不触发任何状态机。CanTp 发现数据 ≤7 字节，贴个标签就发出去了，整条调用链在一次函数返回中完成。

```
CanTp_Transmit → 构建 SF → CanIf_Transmit → return E_OK  (全程同步)
```

### 3.2 FF — 交互的起点："我有大东西要发"

FF 是状态机的**触发器**。发给对端两个信息：

- **12-bit 总长度**——告诉对方要分配多大的缓冲区
- **前 6 字节数据**——趁第一趟车先带过去，一次 CAN 帧能装多少就装多少

FF 发出后，CanTp **不会继续发 CF**——它进入 `WAIT_FC` 状态，**等对方给指令**。

### 3.3 CF — 数据的主力运输队

每个 CF 携带 7 字节数据 + 序号。序号从 1 开始递增（0-15 回绕），接收方用来检测丢帧。CF 的发送节奏完全由 FC 控制，不由发送方自己决定。

### 3.4 FC — 协议的核心："按我的节奏来"

FC 是整个 CanTp 协议最有价值的发明。它承载三种回应：

| Flow Status | 值 | 含义 | CanTp 的反应 |
|-------------|-----|------|-------------|
| **CTS** | 0 | Continue To Send | 提取 BS/STmin → 进入 SENDING_CF |
| **WAIT** | 1 | Wait | 重置超时，继续等 |
| **OVFLW** | 2 | Overflow | 中止本次传输 |

**FC 的两个控制参数**：

| 参数 | 含义 | 例: `BS=8, STmin=10` |
|------|------|----------------------|
| **BS** (Block Size) | 每次允许连续发几个 CF，发完后必须再等一个 FC（0=不限） | 每 8 个 CF 停一下 |
| **STmin** (Min Separation) | 两个 CF 之间最小间隔，单位 100us | 每两个 CF 至少隔 1000us |

## 4. TX 发送过程（完整时序）

用刚学会的概念，走一遍 20 字节数据的完整发送过程：

```
发送方 (我们)                         接收方 (对端)
     │                                      │
     │  ① CanTp_Transmit 被调用              │
     │    数据 > 7 字节，走多帧路径            │
     │    拷贝数据到 tx_buffer               │
     │                                      │
     │── FF [0x10 0x14 D0..D5] ───────────→│
     │   "20 字节要发，前 6 字节在此"           │
     │   状态 → WAIT_FC                      │  ② 提取总长度=20
     │                                      │    分配 rx_buffer
     │                                      │    回复 FC
     │←── FC [0x30 0x08 0x01] ──────────────│
     │   "OK，每次 8 帧，间隔 100us"           │
     │                                      │
     │  ③ 收到 FC(CTS)                      │
     │    状态 → SENDING_CF                   │
     │    BS=8, STmin=100us                 │
     │                                      │
     │── CF [0x21 D6..D12] ────────────────→│  ④ 累积到 rx_buffer
     │── CF [0x22 D13..D19] ────────────────→│  ⑤ rx_index=20=total_length
     │                                      │    提交完整 I-PDU
     │   ⑥ tx_offset=20 ≥ total_length      │    状态 → IDLE
     │     状态 → IDLE                       │
     │     通知 PduR: "发送完成"              │
```

整个过程分为三个阶段：

| 阶段 | 谁在干活 | 干什么 |
|------|---------|--------|
| **启动** (IDLE → WAIT_FC) | `CanTp_Transmit` | 拷贝数据、发 FF、进入等待 |
| **等待** (WAIT_FC) | `CanTp_MainFunction` 检查超时；`CanTp_RxIndication` 收到 FC 后推进 | 等对方给指令 |
| **发送** (SENDING_CF) | `CanTp_MainFunction` | 按 STmin 间隔 + BS 块大小逐帧发 CF |

> **关键设计**：Transmit 只负责"启动"，CF 的实际发送在 MainFunction 中异步完成。这就是为什么 `CanTp_Transmit` 返回 `E_OK` 不等于数据已全部发出——它只是"已受理"。真正的完成通知走 `PduR_CanIfTxConfirmation` 回调。

## 5. RX 接收过程

接收方是发送方的镜像。同样分三种情况：

| 收到 | 处理 |
|------|------|
| **SF** | 跳过 PCI 字节，直接把数据提交给上层（一帧完事） |
| **FF** | 提取总长度→分配缓冲区→立即回复 FC(CTS)→进入 RECEIVING 状态 |
| **CF** | 跳过 PCI 字节→数据追加到 rx_buffer→序号校验→收完提交→回到 IDLE |

**超时保护**（MainFunction 做）：

| 超时 | 触发条件 | 后果 |
|------|---------|------|
| **N_Bs** | 发出 FF 后 1000ms 没收到 FC | 放弃本次发送，回 IDLE |
| **N_Cr** | 进入 RECEIVING 后 1000ms 没收到下一个 CF | 丢弃已接收数据，回 IDLE |

> **注意**：单 MCU 学习场景，如果没有 CAN 回环（外部短接线或内部 Loopback 模式），TX 发出的 FF 永远不会收到 FC → 触发 N_Bs 超时。这是正确行为，不是 bug。

## 6. 代码怎么组织的

```
mcu/Services/CanTp/
├── include/CanTp.h         # 公共 API — 7 个函数声明
├── src/CanTp.c             # 核心逻辑 — ~670 行，所有实现在这里
└── config/
    ├── CanTp_Cfg.h         # 超时参数 + 流控参数 + 通道配置结构体
    └── CanTp_Cfg.c         # 2 个通道: TX(Pdu0→CAN 0x123), RX(Pdu1→CAN 0x100)
```

**CanTp.c 内部结构**（按阅读顺序）：

| 块 | 行号 | 内容 |
|----|------|------|
| 模块常量 | 23-48 | PCI 掩码、帧类型标识、FC 状态码 |
| 通道结构体 | 54-77 | `CanTp_ChannelType` — 每个通道有 RX 上下文 + TX 上下文 + 定时器 |
| CanTp_Init | 194-225 | 初始化 2 个通道，清空所有缓冲区 |
| CanTp_Transmit | 227-321 | TX 入口：≤7B→SF 直发，>7B→FF+进入 WAIT_FC |
| CanTp_RxIndication | 323-535 | RX 分发：SF 透传 / FF 回复 FC / CF 累积 / FC 控制 TX |
| CanTp_MainFunction | 547-660 | 周期驱动：WAIT_FC 超时 / SENDING_CF 节奏 / RECEIVING 超时 |
| CanTp_TxConfirmation | 662-668 | 发送确认（转发 PduR） |
| PCI codec ×5 | 129-188 | SF/FF/CF/FC 的 PCI 构建 + 解码 |

> **提示**：第一次读代码建议按 TX 路径追踪——先看 `CanTp_Transmit`，再看 `CanTp_MainFunction` 的 `SENDING_CF` 分支，最后看 `CanTp_RxIndication` 的 `CANTP_FC` 分支。这三段串联起来就是完整的"FF→FC→CF→IDLE"状态机。

## 7. 几个设计决策——为什么这样做？

### 7.1 为什么 TX 要拷贝数据，而不是直接记住指针？

```c
ch->tx_buffer[i] = srcData[i];  // 拷贝，而不是 ch->tx_src = srcData
```

因为 `CanTp_Transmit` 返回后，调用方的数据可能在栈上、可能被覆盖。但 CF 是异步发送的（MainFunction 中），中间可能隔了几百毫秒。**拷贝保证了数据的生命周期独立于调用方。**

### 7.2 为什么 FC 到达 RX 通道，却能控制 TX 通道？

TX 通道用 CAN ID 0x123 发送 FF，对端用它的 TX ID（即我们的 RX CAN ID 0x100）回复 FC。所以 FC 帧在 RX 通道上到达。代码的处理方式：收到 FC 后遍历所有通道，找到状态为 `CANTP_WAIT_FC` 的来控制——不依赖 FC 走了哪个通道。

### 7.3 为什么分 `PduR_CanIfRxIndication` 和 `PduR_CanTpRxIndication`？

前者处理**含 PCI 的原始 N-PDU**（从 CanIf 来的 CAN 帧），路由到 CanTp 去拆标签。后者处理**不含 PCI 的纯 I-PDU**（CanTp 重组完成的），向上交给 Com。**两条路径必须分开，否则重组完的 I-PDU 会再次进入 CanTp，然后 CanTp 会把数据内容当 PCI 来解析——全乱。**

### 7.4 STmin 为什么是 1ms 而不是配置的 100us？

配置值 `CANTP_STMIN_US = 100`（即 100us），但计时靠 `Log_GetTimeMs()`，分辨率 1ms。100us 被向上取整到 1ms。对于学习项目这不是问题——CF 间隔误差对功能无影响。量产项目需要硬件 µs 定时器。

## 9. 下一步

CanTp 完成后，上层是 **PduR（PDU Router）** 和 **Com（Communication Service）**：

- **PduR**：在 Com ↔ CanTp/CanIf 之间做路由表查表转发——"这个 I-PDU 该走 TP 还是直接发？"
- **Com**：Signal（信号值，比如车速=120km/h）↔ I-PDU（字节序列）的打包/解包——"把这几个信号塞进这个字节布局里"

目前 PduR 有最小实现（直接转发），Com 是骨架。建议按 **PduR → Com** 的顺序继续。
